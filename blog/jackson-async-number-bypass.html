The 10,000-Digit Number: Bypassing Jackson's Async Parser Limits (GHSA-72hv-8253-57qq)

Prabhav Srinath | January 2026 | GHSA-72hv-8253-57qq | CVSS 8.7 High

TL;DR

jackson-core implements a maxNumberLength constraint (default: 1,000 characters) to prevent attackers from sending multi-megabyte numbers that exhaust memory and pin CPU during BigInteger conversion. In synchronous parsers, length validation runs authoritative checks inside resetInt() and resetFloat(). But in the non-blocking async parser (NonBlockingUtf8JsonParserBase), the code finalized numbers by calling _valueComplete() directly, skipping the reset* lifecycle entirely! A 50,000-digit number rejected by synchronous parsers is quietly accepted by the reactive async parser, triggering OutOfMemoryError and $O(n^2)$ CPU starvation. This is GHSA-72hv-8253-57qq (CVSS 8.7), fixed in jackson-core 3.1.0.

How I Discovered This

Right after disclosing the DataInput nesting depth bypass, I asked myself: "What other constraints exist in Jackson's StreamReadConstraints, and which parsers fail to enforce them?"

Jackson supports non-blocking asynchronous parsing for event-driven reactive frameworks (like Spring WebFlux and Vert.x). Because async parsers process byte chunks that arrive over time (chunked non-blocking I/O), they have custom token finalizers.

I inspected NonBlockingUtf8JsonParserBase.java and found _finishNumberIntegralPart(): 

// NonBlockingUtf8JsonParserBase.java
protected void _finishNumberIntegralPart(char[] outBuf, int outPtr) {
    _textBuffer.setCurrentLength(outPtr);
    // BUG: Directly completes token, completely bypassing resetInt() validation!
    _valueComplete(JsonToken.VALUE_NUMBER_INT);
}
"You don't have to fail maxNumberLength checks if you never call validateIntegerLength()"

In the standard synchronous parser, completing a number token calls resetInt() on ParserBase: 

// Synchronous ParserBase.java (Safe Path)
public JsonToken resetInt(boolean negative, int intLen) throws IOException {
    _streamReadConstraints.validateIntegerLength(intLen); // ← ENFORCED!
    ...
    return (_currToken = JsonToken.VALUE_NUMBER_INT);
}
JVM worker thread when asked to construct BigInteger from a 100,000-digit string

Exploitation Impact

  • Memory Exhaustion (OOM): A streaming payload containing {"value": 99999999...} forces Jackson's internal TextBuffer to repeatedly allocate larger char[] chunks until JVM heap memory is exhausted.
  • O(n²) BigInteger CPU Pinning: When downstream application logic deserializes the number into a BigInteger or BigDecimal, the conversion algorithm runs in $O(n^2)$ time complexity, freezing the reactive event loop thread.
  • Reactive Stack Vulnerability: Because async parsers are specifically used in edge proxies and reactive microservices (Spring WebFlux), the systems most exposed to untrusted internet traffic were the ones missing the check.

The Fix

In jackson-core 3.1.0, FasterXML updated the non-blocking token completion routines to explicitly invoke _streamReadConstraints.validateIntegerLength(len) before finalizing value tokens.
