Three Bytes Too Many: Stack Buffer Overflow in BlueZ (GHSA-68h6-5qgp-3975)

Prabhav Srinath | August 2026 | GHSA-68h6-5qgp-3975 | CVSS 7.2 High

TL;DR

A stack-based buffer overflow vulnerability exists in BlueZ, the Linux Bluetooth protocol stack. The vulnerability resides in the name2utf8 function inside src/eir.c. When parsing Extended Inquiry Response (EIR) payloads, the bluetooth daemon (bluetoothd) allocates a 250-byte stack buffer for the device name. If a remote attacker within Bluetooth radio range broadcasts a specially crafted EIR packet carrying a device friendly name of 254 bytes, the parsed name length passed to the conversion function is 253 bytes. The daemon then copies 253 bytes into the 250-byte stack buffer using strncpy, resulting in a 3-byte stack overflow. This leads to an immediate Denial of Service (DoS) crash of bluetoothd and may allow for remote code execution (RCE) on systems with weak stack protections.

The Vulnerability Deep Dive

The vulnerability is located in the name2utf8 helper function inside src/eir.c. This function converts Bluetooth device names (retrieved from EIR packets during active discovery) into UTF-8.

The Vulnerable Code

Let's inspect the conversion function implementation: 

// src/eir.c — name2utf8()
static char *name2utf8(const uint8_t *name, uint8_t len)
{
    char utf8_name[HCI_MAX_NAME_LENGTH + 2]; // 248 + 2 = 250 bytes

    memset(utf8_name, 0, sizeof(utf8_name));
    strncpy(utf8_name, (char *) name, len);   // ← STACK BUFFER OVERFLOW!
    ...
}

Here is how the overflow occurs step-by-step:

  • The buffer utf8_name is declared on the stack with a size of HCI_MAX_NAME_LENGTH + 2. Since HCI_MAX_NAME_LENGTH is defined as 248 in lib/bluetooth/hci.h, the stack buffer size is exactly 250 bytes.
  • The len parameter is a uint8_t, which represents the length of the name field extracted from the incoming EIR packet.
  • When the daemon processes an EIR name field with a field length of 254 (the maximum field size is 255), eir_parse subtracts 1 byte (for the field type header) and passes the remaining 253 bytes as the len argument.
  • Inside name2utf8, the call to strncpy(utf8_name, (char *) name, 253) attempts to write 253 bytes into the 250-byte buffer. This causes an out-of-bounds stack write of exactly 3 bytes.

Exploitation & Impact

Although a 3-byte overflow is small, it occurs directly on the stack frame. Depending on target compiler settings, optimization levels, and stack layout, these 3 bytes can overwrite adjacent critical stack memory. Specifically, it can corrupt control structures like the saved frame pointer, the lowest bytes of the return address, or the stack canary itself.

On platforms lacking active compiler hardening (such as stack canaries/protections) or with predictable layouts, this stack corruption allows an attacker to alter the execution flow and potentially achieve remote code execution (RCE). At a minimum, triggering this overflow immediately crashes the user-space Bluetooth daemon (bluetoothd) with a segmentation fault, creating a zero-click Denial of Service (DoS) for all Bluetooth functionality on the target machine.

Proof of Concept

The following standalone C reproduction isolates the vulnerable name conversion logic and calls it with a 253-byte payload to demonstrate the stack corruption: 

// poc.c — EIR Stack Buffer Overflow PoC
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>

#define HCI_MAX_NAME_LENGTH 248

static void trigger_overflow(const uint8_t *name, uint8_t len)
{
    char utf8_name[HCI_MAX_NAME_LENGTH + 2]; // 250 bytes
    memset(utf8_name, 0, sizeof(utf8_name));
    strncpy(utf8_name, (char *)name, len);   // Overflows here

    printf("[+] Copy completed.\n");
}

int main(void)
{
    uint8_t name_len = 253;
    uint8_t malicious_name[253];
    memset(malicious_name, 'A', sizeof(malicious_name));

    printf("=== EIR Stack Buffer Overflow PoC ===\n");
    trigger_overflow(malicious_name, name_len);
    printf("[!] Execution completed without crashing. (ASan not enabled?)\n");

    return 0;
}

To trace the memory violation, compile the program with AddressSanitizer (ASan) enabled: 

$ gcc -fsanitize=address -g -o poc_runner poc.c
$ ./poc_runner

Running the binary immediately halts the execution with an ASan stack-buffer-overflow trace, detailing the out-of-bounds write past the boundary of utf8_name.

The Fix

The BlueZ maintainers resolved the issue in Pull Request #2339 ("eir: bound remote name length to the local buffer in name2utf8"). The copy length is strictly bounded to the size of the destination stack buffer (leaving room for the null terminator) to prevent stack memory corruption regardless of the size passed in from the EIR payload.

Takeaways

Wireless protocol parsers handle completely untrusted input at a highly privileged layer of the operating system. Even standard libc utilities like strncpy require strict parameter constraints based on local destination sizes, rather than trusting protocol-level maximum field values.
