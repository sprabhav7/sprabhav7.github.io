Tricking nginx's Bounds Check: 32-Bit Integer Overflow in MP4 Module (CVE-2026-27784)

Prabhav Srinath | March 2026 | CVE-2026-27784 | CVSS 8.5 High

TL;DR

ngx_http_mp4_module reads a 32-bit entry count from an MP4 atom header and multiplies it by the entry structure size to calculate the expected table size. On 32-bit builds, that multiplication wraps around before any 64-bit promotion occurs: an entry count of 0x40000001 multiplied by 4 becomes 4. The bounds check compares header_size + 4 > atom_data_size, cheerfully concludes everything fits in the atom buffer, and then nginx uses the original enormous count to advance the heap read pointer straight off the edge of memory. This is CVE-2026-27784 (CVSS 8.5), affecting 7 atom parsers across 32-bit nginx deployments.

How I Discovered This

Media container parsers (MP4, MKV, AVI) are a goldmine for binary vulnerability research. They all share the same structural challenge: a file header specifies an entry count, followed by variable or fixed-length tables, which the parser must safely map into memory buffers.

In nginx, ngx_http_mp4_module handles video pseudo-streaming. When a client requests a video with ?start=10.5, nginx parses sample tables (stts, stss, ctts, stsc, stsz, stco, co64) and rewrites the file layout on the fly.

I was reviewing the atom handlers looking for missing bounds checks. To my surprise, every single atom reader had a clean, well-formatted bounds check right at the top. I almost moved on. But then I looked at the operand types on 32-bit targets.

The Vulnerability Deep Dive

Here is the vulnerable pattern across ngx_http_mp4_module.c: 

/* Read 32-bit entry count directly from untrusted MP4 atom header */
entries = ngx_mp4_get_32value(atom->entries);

if (header_size + entries * sizeof(entry_type) > atom_data_size) {
    return NGX_ERROR;
}

On 32-bit architectures (x86, ARM32, MIPS):

  • entries is uint32_t (32 bits).
  • sizeof(entry_type) evaluates to size_t (32 bits).

Because both operands are 32 bits wide, the multiplication is performed in a 32-bit register. If entries = 0x40000001 and sizeof(uint32_t) = 4:

NGINX bounds check calculating 0x40000001 * 4 = 4
entries      = 0x40000001 (1,073,741,825)
entry size   = 4

True product = 0x100000004 (4,294,967,296 + 4)  /* Requires 33 bits */
32-bit wrap  = 0x00000004 (4 bytes)              /* 33rd bit truncated! */

Bounds check: header_size(8) + 4 > atom_data_size(24)?
              12 > 24 → FALSE! Check BYPASSED!

The guard check answers: "Does 12 bytes fit in 24 bytes? Yes!"

Then, execution continues. The code looks back at the original un-wrapped entries variable (0x40000001) to advance data->pos across the heap!

7 Functions, Same Arithmetic Trap

Because the MP4 module parses seven different atom types with similar fixed-entry structures, the exact same arithmetic wraparound occurs in all seven: 

ngx_http_mp4_read_stts_atom    entry 8 bytes    overflows at entries >= 0x20000001
ngx_http_mp4_read_stss_atom    entry 4 bytes    overflows at entries >= 0x40000001
ngx_http_mp4_read_ctts_atom    entry 8 bytes    overflows at entries >= 0x20000001
ngx_http_mp4_read_stsc_atom    entry 12 bytes   overflows at entries >= 0x15555556
ngx_http_mp4_read_stsz_atom    entry 4 bytes    overflows at entries >= 0x40000001
ngx_http_mp4_read_stco_atom    entry 4 bytes    overflows at entries >= 0x40000001
ngx_http_mp4_read_co64_atom    entry 8 bytes    overflows at entries >= 0x20000001

Exploitation Impact

  • Out-of-Bounds Heap Read/Write: data->pos is advanced past the allocated atom buffer into adjacent heap memory chunks, enabling extraction of neighboring request buffers or secrets.
  • Worker Crash (SIGSEGV): When reading beyond the mapped heap segment, the nginx worker immediately segfaults. Continually requesting the crafted MP4 leads to permanent service outage.
Type promotion in C choosing between 32-bit wrap vs 64-bit safety

The Fix

In nginx 1.29.7, the maintainers resolved this across all affected MP4 atom parsing functions by explicitly casting entry counts to uint64_t prior to multiplication, preventing 32-bit arithmetic wraparound before the buffer bounds check is evaluated.
